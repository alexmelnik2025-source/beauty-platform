# Запуск на сервере в ЕС — пошагово

Инструкция для владельца: как запустить запись GESTALT на своём сервере. Агент ничего не покупает и не
выкладывает — сервер, домен и почту (SMTP) выбирает и оплачивает владелец. Секретов в репозитории нет:
пароли базы и ключ входа создаются прямо на сервере.

## Пошагово (≈ 1 час)

1. **Сервер.** Купите VPS в ЕС с Ubuntu 24.04 (2 ГБ памяти, 2 vCPU, 40 ГБ диска хватит на старт). Добавьте при
   покупке свой SSH-ключ.
2. **Домен.** В панели домена создайте запись `A` для поддомена записи (например `rezerwacje.hairgestalt.pl`)
   на IP сервера. HTTPS-сертификат сервер получит сам, когда запись начнёт работать (обычно 5–60 минут).
3. **Подготовка сервера одной командой** (под `root`):

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/alexmelnik2025-source/beauty-platform/main/scripts/server-setup.sh
   bash server-setup.sh rezerwacje.hairgestalt.pl
   ```

   Скрипт `scripts/server-setup.sh` ставит Docker и Caddy (HTTPS), открывает только порты SSH/80/443, создаёт
   пользователя `beauty`, скачивает код в `/opt/beauty-platform`, создаёт `.env` со случайными паролями,
   включает сайт `https://<домен>` и ежедневную копию базы (03:15 UTC, хранятся 14 дней). Его можно запускать
   повторно — существующие `.env`, код и задания не перезаписываются. Если репозиторий закрытый, перед этим
   скачайте код сами (`git clone` с вашим доступом) в `/opt/beauty-platform`.

4. **Почта.** Впишите в `/opt/beauty-platform/.env` (команда `sudo -u beauty nano /opt/beauty-platform/.env`):
   - `SMTP_URL` — адрес SMTP-сервера с логином и паролем (`smtp://login:hasło@smtp.dostawca.pl:587`);
   - `MAIL_FROM` — отправитель, например `"GESTALT <rezerwacje@hairgestalt.pl>"` (адрес должен быть разрешён
     этим SMTP-сервером, иначе письма уйдут в спам или не уйдут вовсе);
   - `PLATFORM_ADMIN_EMAILS` — ваш e-mail (доступ к очереди писем в кабинете).
5. **Первый запуск:** `sudo -u beauty /opt/beauty-platform/scripts/start.sh` — соберёт приложение, применит
   миграции базы, запустит его и сразу проверит. Скрипт не стартует, пока в `.env` остаются примеры
   (`replace-…`, `example.invalid`).
6. **Проверка** (в любой момент): `sudo -u beauty /opt/beauty-platform/scripts/check.sh` — контейнеры здоровы,
   API отвечает, публичный адрес открывается по HTTPS. Затем вручную: зарегистрируйте салон на
   `https://<домен>/pl/register`, заполните «Ustawienia» (правила и политика), включите запись и запишитесь
   сами по ссылке салона — письмо с кодом и подтверждение должны прийти.
7. **Обновление** до новой версии из `main`: `sudo -u beauty /opt/beauty-platform/scripts/update.sh` —
   новый код, сборка, копия базы, миграции, перезапуск, проверка. Если шаг падает, скрипт останавливается, а
   работающее приложение не трогается до шага перезапуска.
8. **Копии базы** лежат в `/opt/beauty-platform/backups/` (журнал — `backup.log`). Раз в неделю копируйте их за
   пределы сервера (например, `scp` на свой компьютер или в облачное хранилище) и иногда проверяйте восстановление
   (раздел «Резервные копии» ниже).

| Файл                       | Что делает                                                         |
| -------------------------- | ------------------------------------------------------------------ |
| `scripts/server-setup.sh`  | подготовка чистого Ubuntu-сервера (запуск от `root`)               |
| `scripts/start.sh`         | первый запуск после заполнения `.env`                              |
| `scripts/update.sh`        | обновление: git pull → сборка → копия базы → миграции → перезапуск |
| `scripts/check.sh`         | проверка после запуска и обновления                                |
| `scripts/backup.sh`        | копия базы `pg_dump`, удаление копий старше 14 дней (cron)         |
| `deploy/Caddyfile.example` | HTTPS-сайт Caddy: сертификат Let’s Encrypt, прокси на 127.0.0.1    |

CI («Production Docker build») проверяет скрипты ShellCheck, конфигурацию Caddy и что `backup.sh` делает
настоящий дамп поднятой базы и удаляет старые копии.

## Подробности для администратора

Ниже — то же самое вручную, без скриптов: что понадобится, подготовка, первый запуск, копии и откат.

## Что понадобится

- Linux-сервер в регионе ЕС, доступный вам по SSH.
- Docker Engine и Docker Compose plugin, установленные администратором сервера.
- Домен и TLS reverse proxy на самом сервере; наружу публикуйте только HTTPS reverse proxy.
- Работающий SMTP-сервер, если нужны письма.
- Достаточно места для базы и резервных копий.

## Подготовка сервера

1. Установите поддерживаемые дистрибутивом Docker Engine и Compose plugin, создайте отдельную учётную запись для приложения и ограничьте SSH доступ ключами.
2. Получите код из проверенного Git-репозитория и переключитесь на проверенный релизный commit. Не запускайте контейнеры из незнакомой ветки.
3. Скопируйте `.env.example` в `.env`. Замените все значения `replace-*`, `example.invalid` и тестовые SMTP-данные. Не добавляйте заполненный `.env` в Git и не отправляйте его в поддержку.
4. Сгенерируйте `JWT_ACCESS_SECRET` криптографически стойким генератором; он должен иметь не менее 32 символов. Для пароля PostgreSQL используйте длинное URL-safe значение (буквы, цифры, `-`, `_`), чтобы URL подключения не требовал ручного кодирования.
5. Проверьте, что `APP_WEB_URL` — публичный HTTPS адрес, а `SMTP_URL` указывает на SMTP сервер, которым вы управляете. `MAIL_FROM` должен быть разрешён этим сервером.
6. Оставьте VAPID ключи пустыми, чтобы push оставался выключен, либо задайте обе стороны пары, созданной проектным скриптом на доверенной машине. Не передавайте приватный ключ в Git.
7. `PUBLIC_INDEXING=0` закрывает сайт от поисковиков (`robots.txt` запрещает всё). Когда салоны готовы принимать записи из Google, поставьте `PUBLIC_INDEXING=1` и перезапустите `web` (`docker compose -f compose.production.yml up -d web`): откроются только каталог и страницы записи салонов, `sitemap.xml` — `${APP_WEB_URL}/sitemap.xml` (его можно добавить в Google Search Console).
8. Настройте reverse proxy на `http://127.0.0.1:${WEB_PORT}` и включите TLS. Порты API и PostgreSQL в production compose не публикуются на хост.

Перед запуском Docker Compose проверяет обязательные переменные; API дополнительно валидирует окружение при старте и сообщает имена ошибочных переменных без их значений.

## Первый запуск

Проверьте миграции и резервное копирование до применения новых изменений. Миграции запускаются отдельно, не при старте API:

```sh
docker compose --env-file .env -f compose.production.yml build
docker compose --env-file .env -f compose.production.yml up -d postgres
docker compose --env-file .env -f compose.production.yml ps
```

Перед применением миграций сначала снимите резервную копию и изучите SQL-файлы миграций. Запускайте только проверенные миграции, совместимые с текущей версией приложения:

```sh
docker compose --env-file .env -f compose.production.yml --profile maintenance run --rm migrate
docker compose --env-file .env -f compose.production.yml up -d --build api web
docker compose --env-file .env -f compose.production.yml ps
```

Проверьте статус контейнеров и healthcheck, затем откройте публичный HTTPS адрес. Не публикуйте напрямую порты 3000, 4000 или 5432.

## Резервные копии

Сохраняйте копии за пределами этого сервера, шифруйте их и регулярно проверяйте восстановление на отдельной тестовой базе. Ограничьте доступ к резервным копиям теми же мерами, что и к production базе.

Создать согласованный логический дамп PostgreSQL:

```sh
mkdir -p backups
docker compose --env-file .env -f compose.production.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "backups/beauty-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Проверьте, что файл существует, имеет ненулевой размер и был скопирован в защищённое внешнее хранилище. Резервируйте также проверенный commit и заполненный production `.env` в вашем секретном хранилище, но никогда не помещайте секреты в Git или в этот репозиторий.

## Откат

1. Остановите только web и API, оставив PostgreSQL включённым: `docker compose --env-file .env -f compose.production.yml stop web api`.
2. Верните в compose предыдущий проверенный commit/образ приложения и запустите web/API снова. Не запускайте обратные миграции автоматически.
3. Если новая схема несовместима со старой версией приложения, не перезаписывайте текущую базу. Сначала восстановите дамп в отдельную новую базу, проверьте его и переключите `DATABASE_URL` только после подтверждения владельца и наличия проверенной копии текущих данных.
4. После восстановления проверьте `/v1/health`, вход в кабинет и безопасный тестовый сценарий. Сохраните текущие логи и дампы до выяснения причины сбоя.

Удаление текущего volume, `docker compose down -v`, очистка базы и запуск непроверенных миграций не являются шагами штатного отката.
