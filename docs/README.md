## Вход и доступ (задача 2)

| Что                  | Как сделано                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Пароли               | Argon2id, минимум 10 символов                                                                                      |
| Токен доступа        | JWT HS256, 15 минут, в заголовке `Authorization: Bearer`                                                           |
| Refresh-токен        | 30 дней, меняется при каждом обновлении; повтор старого отзывает всю сессию                                        |
| Где хранится refresh | Веб: httpOnly-cookie `bp_refresh` (SameSite=Strict, путь `/v1/auth`); мобильные: в теле ответа → Keychain/Keystore |
| Сессии               | По устройствам: `GET /v1/me/sessions`, выход с устройства — `DELETE`                                               |
| Email                | Подтверждение обязательно до входа; ссылки одноразовые, хранится только хеш                                        |
| Сброс пароля         | Ссылка на 1 час; после сброса все устройства выходят                                                               |
| Ограничение частоты  | Вход: 10 попыток на email за 15 минут; письма: 5 в час на адрес                                                    |
| Изоляция салонов     | Всё под `/v1/organizations/:orgId` проверяет членство; чужое → 404, роль не позволяет → 403                        |
| Роли                 | Владелец — всё; менеджер — только свои филиалы, без создания филиалов; мастер — просмотр                           |

Ограничение частоты хранится в памяти процесса: при нескольких экземплярах API перенесём в PostgreSQL.
Письма подтверждения и сброса отправляются сразу; письма о записях идут через очередь (задача 4).

## Услуги, мастера и свободное время (задача 3)

| Что                  | Как сделано                                                                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Цена                 | Целое число в грошах (`priceGrosze`), без дробей                                                                        |
| Длительность и буфер | Шаг 5 минут; буфер занимает мастера, но не показывается клиенту                                                         |
| Услуги не удаляются  | Выключаются (`active: false`) — на них будут ссылаться записи                                                           |
| Рабочие часы         | Недельный шаблон в местном времени филиала; перерыв = два интервала в день; `24:00` — конец дня                         |
| Особые дни           | Часы на конкретную дату заменяют шаблон в этот день                                                                     |
| Отпуск и блокировки  | Период в местном времени, хранится в UTC; убирает слоты                                                                 |
| Слоты                | Услуга + буфер целиком внутри рабочих часов и вне занятого времени; шаг — из настроек филиала                           |
| Переход времени      | 29.03 часа 02:00–03:00 нет — слотов в нём нет; 25.10 час 02:00 повторяется — слот предлагается один раз                 |
| «Любой мастер»       | Каждый слот содержит список свободных мастеров (`staffIds`)                                                             |
| Для сотрудников      | `GET …/availability` — без минимального срока и горизонта, только не в прошлом                                          |
| Для клиентов         | `GET /v1/public/locations/{slug}/availability` — минимальный срок и горизонт салона; только если включена онлайн-запись |
| Горизонт             | При горизонте 30 дней последний доступный день — сегодня + 30                                                           |
| Защита в базе        | CHECK-ограничения: интервалы, день недели, цена, период отпуска                                                         |

Отложено: категории услуг, переводы названий услуг, приглашение сотрудников в аккаунт (появятся вместе с веб-кабинетом).

## Запись клиента (задача 4)

| Что                         | Как сделано                                                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Шаги онлайн-записи          | 1) удержание слота на 10 минут → 2) имя, телефон, email, согласие → код на email → 3) код → запись подтверждена                     |
| Двойное бронирование        | Запрещено самой базой: `appointment_no_overlap` (EXCLUDE по мастеру и времени с буфером); удержанные и подтверждённые записи        |
| Одновременные запросы       | Запись на одного мастера идёт по очереди (`pg_advisory_xact_lock`), иначе PostgreSQL мог бы прервать их как взаимную блокировку     |
| Истёкшие удержания          | Освобождаются в той же транзакции, что и новая запись — даже если фоновая задача не работает; подтверждение сверяется с часами базы |
| Код                         | 6 цифр, хранится только хеш; живёт не дольше удержания; максимум 3 отправки и 5 попыток                                             |
| Ограничения                 | 5 удержаний на IP за 10 минут, 10 кодов на email в час                                                                              |
| Управление записью клиентом | Ссылка из письма `/{язык}/m/{токен}`: перенос и отмена до срока салона (по умолчанию за 2 часа)                                     |
| Запись салоном              | Телефон, «с улицы»; вне рабочих часов — только с `allowOutsideHours=true`; поверх другой записи — никогда                           |
| Мастер (роль staff)         | Видит и меняет только свои записи                                                                                                   |
| Изменения                   | Номер версии: устаревшая версия → 409 `VERSION_CONFLICT`; история событий у каждой записи                                           |
| Повтор запроса с телефона   | Заголовок `Idempotency-Key`: повтор возвращает тот же ответ; тот же ключ с другим телом → 422                                       |
| Письма                      | Очередь в таблице `notification_outbox`: письмо сохраняется в той же транзакции, что и изменение; 5 попыток с паузами               |
| Дубли писем                 | У каждого письма постоянный ключ; повтор после сбоя не создаёт второе письмо                                                        |
| Напоминание                 | За 24 часа; пропускается, если запись перенесли или отменили                                                                        |
| Персональные данные         | Контакты из неподтверждённого удержания стираются через 24 часа                                                                     |

**Очередь писем — своя, вместо pg-boss (решение 23.10.2026, вариант А).** Укреплена:

- письма берутся по одному, блокировка 5 минут, одна отправка не дольше 1 минуты;
- неотправленные (после 5 попыток) видны администратору платформы: `GET /v1/admin/outbox`, `/failed`,
  повторная отправка `POST /v1/admin/outbox/retry`; страница в кабинете — «Kolejka e-maili»;
- оповещение администраторам (`PLATFORM_ADMIN_EMAILS`) не чаще раза в час, если есть неотправленные или письмо
  ждёт дольше `OUTBOX_ALERT_AFTER_MINUTES` (15);
- очистка: отправленные удаляются через 30 дней, неотправленные — через 90;
- адреса из текстов ошибок провайдера не сохраняются;
- провайдер Resend (`MAIL_TRANSPORT=resend`) получает ключ против дублей (`Idempotency-Key`, 24 часа).
  Проверено на имитации Resend по его документации; на настоящем аккаунте — после его создания.
  Данные аккаунта Resend хранятся в США — решение о провайдере за владельцем (GDPR).

## API для календаря и права мастеров (этап 1)

| Что                      | Как сделано                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Права мастеров           | Категории мастеров с набором прав + личные исключения; итог = исключение → категория → значение по умолчанию                            |
| Проверка прав            | На сервере: чего мастеру нельзя видеть (телефон, email, история, заметки, цена), того нет в ответе API                                  |
| Права по умолчанию       | Можно: создавать, переносить и отменять свои записи. Нельзя: контакты, история, заметки, чужие записи, вне часов, свои деньги           |
| Блокировки времени       | На мастера или на весь филиал, с причиной; не пересекаются с записями (проверка под той же блокировкой, что и запись)                   |
| Календарь одним запросом | `GET …/calendar`: часы мастеров, отсутствия, записи, блокировки. Обновление раз в 30 с с `If-None-Match` → 304, если ничего не менялось |
| Категории и цвет услуг   | Категории с порядком; цвет и порядок у услуги                                                                                           |
| Карточка клиента         | Добавление и правка, заметка салона, метки; история визитов; метки «первый визит» и «мастер выбран клиентом» у записи                   |
| Приглашения              | По email, ссылка на 7 дней, только для того же подтверждённого email; повторное приглашение отменяет старую ссылку                      |
| Удаление из команды      | Доступ пропадает сразу; профиль мастера и записи остаются в календаре                                                                   |
| Лента уведомлений        | `GET /v1/me/notifications`: новая, перенесённая, отменённая запись; пишется в той же транзакции; без контактов клиента                  |

Блокировки и записи хранятся в разных таблицах, поэтому запрет их пересечения проверяется кодом под блокировкой мастера и филиала,
а не правилом базы (как у записей между собой).

## Веб-кабинет и онлайн-запись (этапы 2 и 3)

| Что                 | Как сделано                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Технология          | Next.js (`apps/web`), все страницы — клиентские; браузер обращается к API через тот же адрес (`/v1/*` проксируется) |
| Вход                | Токен доступа только в памяти; refresh — httpOnly-cookie API; после перезагрузки страницы сессия восстанавливается  |
| Языки               | `/pl`, `/uk`, `/ru`, `/en` — переключатель на каждой странице; тексты в `apps/web/lib/i18n`                         |
| Стиль               | GESTALT: чёрное на белом, Michroma для заголовков и времени, скругления 4–6 px; цвет — у услуг и линии «сейчас»     |
| Календарь           | День по мастерам, неделя-полоса, обновление раз в 30 с (ETag → 304), прокрутка к текущему времени                   |
| Права мастера       | Экран показывает только то, что вернул сервер; запрещённые данные (телефон и т. п.) сервер не отдаёт                |
| Онлайн-запись       | `/{язык}/b/{slug}`: услуга → мастер или «любой» → день и время → данные → код → готово (+ файл .ics)                |
| Управление записью  | `/{язык}/m/{токен}` из письма: перенос и отмена до срока салона                                                     |
| Проверка в браузере | CI-задача `e2e`: API + веб + PostgreSQL + Mailpit + Playwright; снимки экранов — в ветке `e2e-screenshots`          |

Отклонения и ограничения:

- В спецификации — типизированный клиент `packages/api-client`, сгенерированный из OpenAPI. Сделано для всего, что
  видит клиент, и для кабинета: вход, организации, филиалы, услуги, мастера, записи, клиенты, блокировки, календарь
  (см. «Типы API из OpenAPI»); права пока написаны вручную (`apps/web/lib/types.ts`).
- В шрифте Michroma нет кириллицы: на украинском и русском заголовки показываются основным шрифтом.
- API за прокси веб-сервера должен знать адрес посетителя: `TRUST_PROXY=1` (иначе лимиты частоты считаются на всех вместе).

## Приложение на телефон и компьютер (этап 4, начало)

Кабинет салона ставится как приложение (PWA) — без App Store и Google Play:

| Где                        | Как установить                                                          |
| -------------------------- | ----------------------------------------------------------------------- |
| Android, Chrome, Edge      | кнопка «Zainstaluj aplikację» в меню «Więcej» или внизу боковой панели  |
| iPhone, iPad               | Safari → «Udostępnij» → «Do ekranu początkowego» (шаги показаны там же) |
| Mac, Windows (Chrome/Edge) | та же кнопка или значок установки в адресной строке                     |

- Манифест — на языке интерфейса (`public/manifests/salon-{pl,uk,ru,en}.webmanifest`), у всех один `id`,
  поэтому это одно приложение; запуск — `/{язык}/app`.
- Service worker (`public/sw.js`) не хранит данные салона на устройстве: страницы и `/v1/*` всегда из сети,
  в кеше только страница «нет соединения».

**Push-уведомления (Web Push).** Новые, перенесённые и отменённые записи приходят на телефон и компьютер,
даже когда приложение закрыто. Включаются в «Więcej» и «Powiadomienia» → «Włącz powiadomienia» на каждом устройстве.

| Что           | Как сделано                                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| Источник      | Лента уведомлений: строка пишется в транзакции изменения записи, фоновая задача отправляет ещё не отправленные       |
| Надёжность    | `FOR UPDATE SKIP LOCKED`, до 3 попыток; старше 1 часа не отправляются (в ленте остаются)                             |
| Устройства    | `POST /v1/me/push-subscriptions`, выключить — `…/remove`; отписавшееся устройство (404/410) удаляется сразу          |
| Текст         | На языке пользователя: время, клиент, услуга, мастер — без телефона и email (видно на экране блокировки)             |
| Ключи         | `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` (новая пара: `node apps/api/scripts/vapid-keys.mjs`); без них push выключен |
| iPhone и iPad | Только в установленном приложении (iOS 16.4+); в Safari без установки — подсказка «сначала установите»               |
| Тесты         | `PUSH_TRANSPORT=memory`: отправка, повтор, удаление отписавшегося устройства, отказ после 3 попыток                  |

- Иконки — из логотипа GESTALT (`public/icons`).

## Приложение клиента «Мои визиты» (этап 4, задача 1)

Клиент входит без пароля и видит свои записи во всех салонах платформы. Вход клиента отделён от аккаунтов салонов.

| Что                | Как сделано                                                                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| Вход               | `POST /v1/client/auth/code` (email) → письмо с 6-значным кодом → `POST /v1/client/auth/verify`                  |
| Код                | 10 минут, хранится только хеш, одноразовый; 5 неверных попыток → новый код; 5 кодов в час на адрес              |
| Без «прощупывания» | Ответ одинаковый, есть у адреса визиты или нет                                                                  |
| Сессия             | 90 дней. Веб: httpOnly-cookie `bp_client` (путь `/v1/client`); мобильные: токен в теле → `Bearer`; хранится хеш |
| Person             | Клиент платформы по подтверждённому email (задел из спецификации); язык писем — `PATCH /v1/client/me`           |
| Какие визиты видны | Записи карточек клиентов салонов с тем же email: подтверждённые, отменённые, завершённые, неявки; не удержания  |
| Списки             | `GET /v1/client/appointments?scope=upcoming` (ближайшие первыми) и `scope=past` (последние 50)                  |
| Отмена и перенос   | `POST …/appointments/{id}/cancel` и `/reschedule` — те же правила и письма, что и по ссылке из письма           |
| Чужая запись       | Выглядит как несуществующая (404)                                                                               |
| «Записаться снова» | В ответе `bookAgain`: салон, услуга, мастер; `null`, если салон больше не принимает эту услугу онлайн           |
| Что не отдаётся    | Заметки и метки салона, контакты — только то, что клиент видит по ссылке из письма                              |
| Очистка            | Неиспользованные коды удаляются через сутки после истечения, истёкшие сессии — сразу                            |

Записи, которые салон внёс с email клиента вручную, тоже видны владельцу этого email (как в Booksy по телефону).

**Экраны** (`/{язык}/c`):

| Экран                  | Что там                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| Вход                   | E-mail → код из письма; «Wyślij kod ponownie», «Inny e-mail»; после перезагрузки сессия сохраняется    |
| Список                 | Вкладки «Nadchodzące» и «Historia»: время, услуга, мастер, цена, салон; в истории — «Umów ponownie»    |
| Визит `/{язык}/c/{id}` | Тот же экран, что и по ссылке из письма (общий компонент): перенос, отмена, файл .ics, «Umów ponownie» |
| «Umów ponownie»        | Страница записи салона с `?service=…&staff=…` открывается сразу на выборе времени                      |
| После записи           | На экране «Do zobaczenia!» — ссылка «Wszystkie moje wizyty»                                            |

Проверка в браузере: шаг в основном e2e-сценарии (вход по коду из Mailpit, список, визит, «Umów ponownie»).
**Установка на телефон.** «Мои визиты» — отдельное приложение, не кабинет салона: свой манифест
(`public/manifests/visits-{pl,uk,ru,en}.webmanifest`, `id: /c`, запуск — `/{язык}/c`), название
«GESTALT · Wizyty» (UA «Візити», RU «Визиты», EN «Visits»), тот же service worker. Кнопка «Zainstaluj aplikację»
и шаги для iPhone — под списком визитов.

## Страница записи помнит клиента (задача 2)

| Что                 | Как сделано                                                                                                    |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| Галочка             | «Zapamiętaj mnie na tym urządzeniu» на шаге данных; по умолчанию выключена (согласие клиента)                  |
| Что хранится        | Имя, телефон, email — только в браузере этого устройства (`localStorage`, ключ `bp_booking_contact`)           |
| В следующий раз     | Поля заполнены, галочка стоит; «To nie ja — wyczyść dane» стирает данные (для чужого устройства)               |
| Вход в «Мои визиты» | С галочкой `confirm` получает `signIn: true`: код из письма уже подтвердил email, сервер ставит cookie клиента |
| Токен               | Только в httpOnly-cookie `bp_client`, в ответе (и в сохранённом ответе для повтора запроса) его нет            |
| После записи        | Карточка «Wizyta jest już w aplikacji» → «Zainstaluj aplikację» открывает «Мои визиты», запись уже там         |
| Без галочки         | Всё как раньше: ничего не хранится, сессии нет, ссылка «Wszystkie moje wizyty» ведёт ко входу по коду          |

Проверка: API-тесты (cookie, визит виден сразу, повтор запроса не создаёт вторую сессию, неверный код никого не
впускает) и шаг e2e (второй клиент с галочкой → приложение без входа → поля заполнены → «To nie ja»).

## Код по SMS или email (задача 4, без SMS-шлюза)

Клиент на странице записи выбирает, куда прислать код: «E-mail» (по умолчанию) или «SMS». Настоящий польский
SMS-шлюз платный и подключается только после решения владельца — сейчас SMS только «на бумаге».

| Что               | Как сделано                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| Отправка SMS      | `SmsService`, как письма: `memory` (тесты), `log` (разработка — текст с кодом в логе API), `none`          |
| Настройка         | `SMS_TRANSPORT`, по умолчанию `none`; в production разрешён только `none`, пока не выбран шлюз             |
| Когда видна опция | Страница салона отдаёт `codeChannels`: `['email']` или `['email', 'sms']` (если отправка SMS работает)     |
| API               | `POST /v1/public/holds/{id}/code` + `codeChannel: 'email' \| 'sms'`; без шлюза — ошибка `SMS_UNAVAILABLE`  |
| Текст SMS         | Короткий, на языке клиента: «123456 — kod rezerwacji w {salon}. Ważny 10 min.»                             |
| Лимиты            | 3 кода на одно удержание (как раньше) и не больше 5 SMS в час на номер — каждое SMS стоит денег            |
| Что подтверждает  | SMS-код подтверждает телефон, не email: вход в «Мои визиты» не выполняется, карточку клиента салона с этим |
|                   | email запись не перезаписывает. Письмо с деталями визита по-прежнему уходит на email                       |

Подключение шлюза позже: новый класс `SmsService` (HTTP API шлюза) и значение `SMS_TRANSPORT`; остальной код не меняется.
Проверка: API-тесты (SMS вместо письма, язык, лимиты, неверный код, без шлюза, карточка не перезаписывается) и шаг e2e
(клиент выбирает SMS, код читается из лога API).

## Кнопка записи для сайта и Instagram (задача 5)

| Что                   | Как сделано                                                                                                       |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Короткая ссылка       | `/s/{салон}` → страница записи на языке телефона клиента (`Accept-Language`, иначе PL); `utm_…` сохраняются       |
| Кнопка для сайта      | `<script src="…/embed.js" data-salon="{салон}" data-lang="pl" async>` — кнопка «Umów wizytę» в углу               |
| Окно записи           | Страница записи салона в окне поверх сайта (`?embed=1`); загружается при первом нажатии; × и Esc закрывают        |
| Своя кнопка/ссылка    | Любой элемент с `data-bp-book` открывает окно; `data-button="none"` скрывает плавающую кнопку                     |
| Настройки кнопки      | `data-label` (текст), `data-color` (`#rrggbb`), `data-position="left"`; текст кнопки на 4 языках                  |
| Чужие сайты в рамке   | Только страница записи `/{язык}/b/{салон}` может открываться внутри другого сайта; всё остальное — `DENY`         |
| В окне на чужом сайте | Без «Zapamiętaj mnie» (чужой сайт не хранит данные клиента), ссылки «Zarządzaj» и «Moje wizyty» — в новой вкладке |
| В кабинете            | «Ustawienia» → «Instagram i Twoja strona»: короткая ссылка и код кнопки с «Kopiuj»                                |
| QR-код салона         | Там же: QR короткой ссылки (`/s/{салон}?utm_source=qr`), «Pobierz PNG» (≈1400 px), «Pobierz SVG», «Drukuj»        |
| Печать QR             | Печатается только карточка: QR, название салона, «Zeskanuj i umów wizytę», адрес ссылки (`html.print-qr`)         |

Проверка: шаг e2e — ссылки в настройках, переход по короткой ссылке (язык, `utm`), заголовки рамки, сайт салона
на другом адресе с кодом из кабинета → окно записи с услугами, закрытие, своя ссылка `data-bp-book`;
QR — скачивание PNG и SVG (имя файла, размер, ссылка внутри), печать только карточки.
QR-код строит собственный модуль `apps/web/lib/qr.ts` (без зависимостей; байтовый режим, уровень коррекции M,
версии 1–40, выбор маски по стандарту). Проверен декодером OpenCV на ссылках длиной 19–2268 байт (версии 2–40).

## Фото салона и мастеров (задача 6, часть 2: API)

| Что           | Как сделано                                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| Где хранятся  | В базе (таблица `photo`, `BYTEA`) — без платных хранилищ. Удаляются вместе с салоном или мастером               |
| Фото салона   | До 10 штук: `GET/POST …/locations/{id}/photos`, `DELETE …/photos/{photoId}`                                     |
| Фото мастера  | Одно на мастера: `PUT/DELETE …/staff/{staffId}/photo`; новое фото заменяет старое                               |
| Как загружать | Тело запроса — сама картинка (`Content-Type: image/…`), не форма. До 3 МБ; веб будет уменьшать фото до отправки |
| Тип файла     | Только JPEG, PNG, WebP — по первым байтам файла, а не по заявленному типу (SVG, HTML и прочее отклоняются)      |
| Кто меняет    | Владелец и менеджер своего салона; мастер только видит (403); чужой салон или чужой мастер — 404                |
| Показ         | `GET /v1/public/photos/{id}` — без входа; у каждого фото случайный id, новое фото = новая ссылка (кэш на год)   |
| Где видно     | Страница салона отдаёт `photos: [{id, url}]` и `staff[].photoUrl`; список мастеров в кабинете — `photoUrl`      |

Проверка: API-тесты (загрузка, список, показ с заголовками, удаление, тип по байтам, SVG/JSON/пустой файл, больше 3 МБ,
лимит 10 фото, права мастера, чужой салон и менеджер другого филиала, замена и удаление фото мастера).
Дальше (часть 3): загрузка фото в кабинете (уменьшение в браузере), фото на странице записи и выбор мастера с фото.

## Формат ошибок API

```json
{ "error": { "code": "NOT_FOUND", "message": "...", "requestId": "..." } }
```

`code` — машинный код; веб и мобильные приложения переводят его на язык пользователя.
Коды: `VALIDATION_ERROR` (+ `details`), `UNAUTHORIZED`, `INVALID_CREDENTIALS`, `EMAIL_NOT_VERIFIED`,
`INVALID_TOKEN`, `INVALID_REFRESH_TOKEN`, `FORBIDDEN`, `NOT_FOUND`, `SLUG_TAKEN`, `VERSION_CONFLICT`,
`RATE_LIMITED`, `STAFF_SERVICE_MISMATCH`, `SLOT_TAKEN`, `OUTSIDE_WORKING_HOURS`, `IN_THE_PAST`, `TOO_LONG_AGO`, `NOT_STARTED`,
`HOLD_EXPIRED`, `CODE_NOT_SENT`, `CODE_EXPIRED`, `INVALID_CODE`, `TOO_MANY_ATTEMPTS`, `TOO_MANY_CODES`, `TOO_LATE_TO_CHANGE`,
`SMS_UNAVAILABLE`, `PHOTO_TOO_LARGE`, `UNSUPPORTED_PHOTO`, `TOO_MANY_PHOTOS`, `IDEMPOTENCY_KEY_REUSED`, `REQUEST_IN_PROGRESS`, `CATEGORY_NAME_TAKEN`, `INVITATION_EXPIRED`, `EMAIL_MISMATCH`,
`ALREADY_MEMBER`, `STAFF_ALREADY_LINKED`, `CANNOT_REMOVE_OWNER`, `INTERNAL_ERROR`.
Каждый ответ содержит заголовок `x-request-id` для поиска запроса в логах.

## Типы API из OpenAPI (задача 7 — готово)

Один источник правды для формы ответов: схема zod в API. Из неё — тип в коде API, документ OpenAPI и типы для
веба и будущих приложений.

| Что                  | Как сделано                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| Описание ответа      | `responseSchema('Имя', z.strictObject(…))` рядом с модулем (`*.responses.ts`) + `@ApiZodResponse` у метода      |
| Документ             | `packages/api-client/openapi.json` (тот же, что на `/v1/docs-json`), `components.schemas.<Имя>`                 |
| Типы                 | `packages/api-client/src/schema.d.ts` — генерирует `openapi-typescript`; удобные имена в `src/index.ts`         |
| Использование в вебе | `apps/web/lib/types.ts` переэкспортирует сгенерированные типы из `@beauty/api-client`                           |
| Проверка             | Тест `openapi.spec.ts`: документ совпадает с сохранённым; настоящие ответы совпадают со схемой без лишних полей |
| CI                   | Шаг «API client matches OpenAPI»: падает, если `schema.d.ts` не перегенерирован                                 |
| Клиент (часть 1)     | Страница салона, свободное время, шаги записи, ссылка управления, «Мои визиты» (12 схем)                        |

## Вход по коду без пароля для бизнес-приложения (задача 11a, часть 1)

Доступ даёт только владелец (или менеджер — мастерам своих филиалов): он приглашает человека по email и выбирает
роль. Человек входит по email и коду из письма — без пароля и без регистрации — и сразу попадает в свой салон
с нужной ролью. Пока это API; экраны — в бизнес-приложении (следующие части 11a).

| Что                       | Как сделано                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Код                       | `POST /v1/auth/code {email, locale}` → письмо с 6-значным кодом, 10 минут, хранится только хеш (`staff_login_code`)      |
| Вход                      | `POST /v1/auth/code/verify {email, code, clientType}` → те же токены, что и при входе по паролю (mobile: refresh в теле) |
| Первый вход приглашённого | Аккаунт создаётся сам (имя — из профиля мастера в календаре или `name`), email считается подтверждённым                  |
| Приглашения               | При входе по коду принимаются все действующие приглашения на этот email: роль, филиалы, категория прав, профиль мастера  |
| Без самозаписи            | Нет аккаунта и нет действующего приглашения → код не отправляется; ответ одинаковый для любого адреса                    |
| Отменённое приглашение    | Отменили после отправки кода → `403 NO_INVITATION`, аккаунт не создаётся                                                 |
| Защита                    | Код одноразовый; 5 неверных попыток → нужен новый; 5 писем в час на адрес; коды салона и клиента не взаимозаменяемы      |
| Пароль                    | У существующих аккаунтов пароль продолжает работать; созданные по коду могут задать пароль через «Забыли пароль»         |
| Проверки                  | `code-login.spec.ts`                                                                                                     |

## Вход по номеру телефона (задача 11a, часть 2)

## Тест-фиксы 03.11.2026 (T2, T3, T4)

- **Без дублей (T4):** формы кабинета (услуга, специалист, визит/блок, категория) блокируются на время
  сохранения (`lib/submit-lock.ts`), а «добавить» отправляет один `Idempotency-Key` на форму. POST услуг,

- **Список обновляется сразу (T2):** сохранённая услуга сразу видна в списке; все ответы API идут с

## Тест-фикс 03.11.2026: «Кто выполняет услугу?» (T5)

- Клиент видит услугу на странице записи, только если её выполняет хотя бы один активный специалист. Раньше
  новая услуга «пропадала» без подсказки, пока её не отметили у мастера в «Zespół».
- API: у услуги есть `staffIds` (кто её выполняет); `POST …/services` принимает `staffIds`, а
  `PUT …/services/:serviceId/staff` заменяет список (только владелец/менеджер; специалисты другого салона —

  работает как раньше — это та же связь с другой стороны.
- Кабинет: в окне услуги — «Kto wykonuje tę usługę?» с галочками специалистов (для новой услуги отмечены все,

  nie widzą». Тест — `apps/api/test/service-staff.spec.ts`, скриншоты e2e 50–51.

## Клиентское приложение: запись в приложении (задача 11b, часть 4б)

- На странице салона «Umów wizytę» теперь открывает запись прямо в приложении (раньше — сайт). Вход не нужен.
- Шаги как на сайте: услуга (по группам прайса) → специалист или «Dowolny specjalista» (если услугу делает один
  мастер — шаг пропускается) → день и свободное время на 3 недели вперёд (утро / день / вечер, в поясе салона) →
  время держится 10 минут (обратный отсчёт; истекло — снова выбор времени) → имя, телефон (`600 100 200` → `+48…`),
  e-mail, галочка «Akceptuję zasady rezerwacji…» (обязательно) и «wiadomości o nowościach» (по желанию) → код из
  e-maila → «Do zobaczenia!». Тот же API, что у страницы записи: `POST /v1/public/locations/:slug/holds`
  (`Idempotency-Key`), `…/holds/:id/code`, `…/holds/:id/confirm` (ключ `confirm-<hold>-<код>`, как на вебе),
  при уходе с записи время освобождается (`…/release`).
- Ошибки — те же тексты, что на сайте: время заняли — свежий список; 10 минут прошли, 3 кода, много попыток — снова
  выбор времени; неверный код — остаёмся на шаге кода. Поля проверяются до отправки на сервер.
- После записи: вошедший клиент — «Moje wizyty» (список перечитывается, визит уже там); не вошедший —
  «Zaloguj się do „Moich wizyt”» (экран входа с уже вписанным e-mail) и «Zmień lub odwołaj wizytę» (ссылка из письма).
  Токен сессии при записи приложению не выдаётся (так задумано на сервере: токен не попадает в тело ответа).
- Пока только код по e-mail (SMS — после подключения шлюза). «Umów ponownie» и «Umów się» — тоже в приложении
  (часть 5).
- Код: `availability` / `hold` / `sendBookingCode` / `confirmBooking` / `releaseHold` в `src/api.ts`, `src/booking.ts`
  (проверка формы, телефон, части дня, отсчёт), `src/screens/BookingScreen.tsx`; тесты `test/booking.test.ts`; e2e —
  скриншоты `64-client-app-book-service`, `64a-client-app-book-time`, `64b-client-app-book-details`,
  `64c-client-app-booked`.

## Правила и политика конфиденциальности салона (задача запуска L1)

- У каждого салона свои тексты: «Regulamin rezerwacji» и «Polityka prywatności» (Markdown: `#`/`##` заголовки,
  списки `1.` и `-`, пустая строка — новый абзац). Пишутся в кабинете: «Ustawienia» → «Regulamin i prywatność».
- **Без обоих текстов онлайн-запись нельзя включить** (ошибка `LEGAL_TEXTS_REQUIRED`, понятный текст на 4 языках),
  и нельзя стереть текст, пока запись включена. Салоны, которые уже принимали записи до этой функции, продолжают
  работать и сохраняют другие настройки — проверка срабатывает при включении записи или при удалении текста.
- «Wstaw szablon» — польский шаблон из `docs/legal/` с уже вписанными данными салона: название, адрес, юр. название,
  NIP, телефон, e-mail, срок изменений («2 godzin przed wizytą» из настройки салона), ссылка на политику. Под полями —
  «Do uzupełnienia: {KRS}, {ADRES_FIRMY}…» — что салон вписывает сам. Шаблон не сохраняется, пока не нажать «Zapisz»;
  в тексте есть пометка, что его надо проверить с юристом.
- Клиент видит тексты на `/<язык>/b/<slug>/regulamin` и `/<язык>/b/<slug>/privacy`; галочка в записи теперь
  «Akceptuję regulamin rezerwacji i politykę prywatności salonu.» со ссылками на обе страницы. В клиентском
  приложении — две ссылки под галочкой, открывают те же страницы на сайте.
- API: поля `bookingTerms`, `privacyPolicy` у салона (`PATCH /v1/organizations/:org/locations/:id`, до 50 000 знаков,
  пустая строка — удалить), `GET …/locations/:id/legal-templates` (владелец и менеджер салона; ничего не
  сохраняет), `GET /v1/public/locations/:slug/legal` (только для салона с включённой записью). Миграция
  `20261104120000_location_legal_texts`. Шаблоны в коде (`apps/api/src/organizations/legal-templates.ts`) — копия
  `docs/legal/*.pl.md`; тест `test/legal-texts.spec.ts` падает, если файлы разошлись.
- Тексты показываются без HTML из текста (свой маленький разбор Markdown в `apps/web/components/Markdown.tsx`).
- e2e — скриншоты `65-owner-legal-texts` (поля и шаблон в настройках), `66-client-booking-terms` (страница
  правил для клиента), `64b-client-app-book-details` (ссылки в приложении).

## Валюта салона (задача запуска L5, часть 1)

- У каждой точки (салона) своя валюта — как и часовой пояс: «Ustawienia» → «Waluta cen» (по умолчанию PLN).
  Список: PLN, EUR, CZK, HUF, RON, SEK, DKK, NOK, CHF, GBP, ALL, TRY, MKD, RSD, BAM, MDL, UAH, GEL, AMD, AZN, KZT,
  KGS, UZS, TJS, TMT, BYN, RUB, USD (ЕС, СНГ, Албания, Турция). Названия валют — на языке интерфейса (Intl).
- Суммы по-прежнему в сотых долях валюты (поля `…Grosze`: 50,00 € = 5000, 500 ₺ = 50000). Смена валюты **не
  пересчитывает** цены — салон правит их в «Usługi» (подсказка под полем).
- Цены показываются в валюте салона везде: список и форма услуг («Cena (€)»), календарь и карточка визита, страница
  записи и шаги записи, ссылка «управлять визитом», «Moje wizyty» и «Moje bonusy» (сайт и клиентское приложение),
  бизнес-приложение, письма клиенту и салону; в программе лояльности — «za każde (€)», «Minimalna kwota wizyty (€)».
- API: поле `currency` (ISO 4217) у точки (`PATCH /v1/organizations/:org/locations/:id`, только коды из списка, иначе
  `VALIDATION_ERROR`) и в ответах: точка, публичная страница салона, удержание времени (`Hold`), визит клиента
  (`PublicAppointment`, `ClientAppointment`), календарь (`location.currency`), карта бонусов клиента. Список — в
  `apps/api/src/common/currency.ts`; в вебе тот же список проверяется типом `Currency` из `@beauty/api-client`.
  Миграция `20261104150000_location_currency`, тест `test/currency.spec.ts`.
- e2e — скриншоты `67-owner-currency` (выбор валюты), `67b-owner-service-price-euro` (услуги в евро),
  `67c-booking-prices-euro` (страница записи в евро).

## Запуск на сервере пошагово (задача запуска L3)

- `docs/DEPLOY.md` начинается с «Пошагово» для владельца: VPS в ЕС → запись `A` в DNS → `server-setup.sh` →

  базы и удаляет старые.

## Блокировка времени каждую неделю (задача запуска L4)

## Купон клиента на визите (задача 10d, часть 1 — API)

- Сотрудник применяет купон клиента к визиту: выбирает из списка или вводит код, который клиент показывает
  (`k7qm 4xtb` = `K7QM-4XTB`). Цена визита (`priceGrosze`) не меняется — рядом хранится скидка `discountGrosze`,
  клиент платит разницу; у визита — список `coupons`.
- Правила салона проверяет сервер: купон только этого клиента и этого салона (чужой → 404), не просроченный, на
  услугу визита (у «бесплатной услуги» — только та услуга, она бесплатна целиком); без «łączenie rabatów» — один
  купон на визит; процентные скидки вместе не больше «maks. rabat %» салона, никогда ниже нуля; копейки — вниз.
- Купоны меняются только у записанного или «пришёл» визита до отметки «оплачено». После оплаты бонусы считаются с
  оплаченной суммы (80 zł − 25 % = 60 zł → 6 баллов при 10 за 100 zł). Чтобы снять купон с оплаченного визита —
  сначала «не оплачено».
- Отмена визита (салоном или клиентом) и «не пришёл» возвращают купон клиенту (`couponsReturned` в истории).
  В истории визита — «Użyto kuponu» / «Zdjęto kupon» (4 языка).
- Купон, который уже действует, работает и при выключенной программе.
- API: `GET …/appointments/:id/coupons` (использованные и остальные купоны клиента: сколько снимет или почему
  нельзя — `problem`), `POST …/appointments/:id/coupons` `{version, couponId | code}`,
  `POST …/appointments/:id/coupons/:couponId/remove` `{version}`. Права — как у «оплачено» (свой визит / все).
  Ошибки 409: `COUPON_NOT_FOR_SERVICE`, `COUPON_NOT_COMBINABLE`, `COUPON_NO_DISCOUNT`, `COUPON_EXPIRED`,
  `COUPON_NOT_ACTIVE`, `VISIT_NOT_CHANGEABLE`, `VERSION_CONFLICT`.

## Бонусы по мастеру и дням недели (задача 19)

Салон сам задаёт правила «больше отметок или баллов»: у выбранных мастеров и/или в выбранные дни недели
оплаченный визит даёт ×N (1–10) и/или +N сверху — например, «×2 в пн–ср у Ильи», чтобы заполнить спокойные дни.

- API: `GET/PUT /v1/organizations/:orgId/loyalty/bonus-rules` — весь список целиком (до 20 правил, пустой —
  выключить). Только владелец и менеджер; мастер в правиле — только этого салона, менеджер называет только
  мастеров своих точек (иначе 404). Правило без выгоды (×1 и +0), несуществующий день или повтор — 400.
- Начисление (`LoyaltyLedger.earnForVisit`): база по обычным правилам × множитель + добавка по **самому выгодному**
  подходящему правилу (правила не складываются). День недели — по часовому поясу салона (визит в 00:30 понедельника
  по Варшаве — понедельник). Если визит сам ничего не даёт (ниже минимальной суммы, правило услуги «0»), бонуса
  тоже нет. В истории операций у начисления заметка «Название правила: 10 → 20».
- «Если клиент возвращается в течение N дней» (`withinDays`, 1–365, задача 19c): правило действует, только если
  предыдущий **оплаченный** визит клиента в этом салоне был не раньше чем за N календарных дней (по поясу салона) —
  «каждая стрижка при визитах раз в 3 недели ×2». Первый визит и неоплаченные визиты не считаются.
- Кабинет: блок «Dodatkowe pieczątki i punkty» в «Program lojalnościowy» — название, мастера, дни, «Mnożnik (×)»,
  «Dodatkowo (+)», «Gdy wraca w ciągu (dni)»; 4 языка; скриншот 79.
- Клиент видит правила (задача 19d): в «Moje bonusy» на сайте и в клиентском приложении — блок «Więcej za wizytę»
  («Spokojne dni ×2 — pon., wt., śr. · u: Kasia · gdy wracasz w ciągu 21 dni»), 6 языков; API — поле `bonuses` в
  `GET /v1/client/loyalty` (только при включённой программе; правило только для ушедших мастеров не показывается).
- База: таблица `loyalty_bonus_rule` (CHECK: множитель 1–10, добавка 0–100 000, хоть что-то сверху, дни 1–7).
  Тесты: `apps/api/test/loyalty-bonus-rules.spec.ts`.

## Lista oczekujących — лист ожидания (задача 50)

- API: `POST /v1/public/locations/:slug/waitlist` (услуга, мастер или любой, день; 409 `SLOTS_AVAILABLE` — в этот день

## Пожелания к визиту (задача 80, часть 80a — API)

- Салон в настройках точки включает вопросы последнего шага записи: `askMood` (как провести визит: `chat` / `quiet` /
  `relax`, по умолчанию вкл.), `askDrink` + `drinks` (что салон предлагает: `coffee`, `tea`, `water`; клиент может

  задаёт, и напитки, которых нет, отбрасываются молча (страница могла быть открыта до смены настроек). Ответы пишутся в

## Ochrona przed odwołaniami — защита от отмен (задача 161, часть 161a — API)

Решение владельца 05.11.2026: салон сам включает правила для клиентов, которые часто отменяют, переносят или не
приходят. По умолчанию выключено. Настройки — у каждой точки, только владелец и менеджер этой точки:

- `GET/PUT /v1/organizations/:orgId/locations/:locationId/cancellation-guard` — `enabled`, `maxChanges` (N
  отмен/переносов клиентом) за `windowHours` (X часов), `lateCancelMinutes` (отмена позже чем за Y минут — одна
  такая отмена уже отмечает клиента), `maxNoShows` (M неявок), `action`: `approval` (запись только с
  подтверждением салона), `phone_only` (только по телефону), `prepay` (сначала оплатить пропущенные визиты в
  салоне). Правило `null` не действует; включить без единого правила нельзя (400). `version` — 0 до первого
  сохранения, 409 при одновременной правке. Изменение пишется в «Dziennik zmian».
- `GET …/cancellation-guard/clients` — кто отмечен сейчас: причины (`changes`, `late_cancel`, `no_shows`),
  счётчики и сумма пропущенных визитов (цена после скидок, валюта салона). Пока защита выключена — пусто.
- `GET …/cancellation-guard/clients/:customerId` — отметка и история клиента (отмены, переносы, неявки, снятия
  блокировки) за год.
- `POST …/cancellation-guard/clients/:customerId/release` `{ note? }` — «Zdejmij blokadę»: счёт начинается
  заново, история остаётся.

Ничего не хранится «про запас»: отметка каждый раз считается по истории визитов этой точки (события отмены и
переноса от клиента, визиты «nie przyszedł» за последние 365 дней после последнего снятия). Для записи —
`CancellationGuardService.check(locationId, customerId)` (часть 161b). Онлайн-оплаты нет: при `prepay` клиент
платит в салоне, салон снимает блок вручную.

**161c — кабинет.** Меню «Ochrona przed odwołaniami» (владелец и менеджер): включение, три правила с числами
(отмены/переносы за N дней, поздняя отмена в минутах, неявки), что делать с отмеченным клиентом; ниже — список
отмеченных клиентов с причинами, телефоном и суммой пропущенных визитов, «Zdejmij blokadę» с заметкой. 4 языка кабинета, e2e
`cancellation-guard-cabinet.spec.ts`, скриншоты 161e–161f. В карточке клиента (владелец и менеджер) — блок
«Ochrona przed odwołaniami» (`components/guard/ClientGuard.tsx`, `GET …/cancellation-guard/clients/:id`): отмечен ли
клиент и почему, сумма неявок, «Zdejmij blokadę» с заметкой и история за год; при выключенной защите и пустой
истории блока нет. Скриншот 161g. То же в карточке клиента бизнес-приложения (`ClientScreen`,
`BusinessApi.guardClient` / `releaseGuard`; 5 последних событий), скриншот 161h.

## Выход из кабинета при быстром F5 (задача 204)

`SessionProvider.load` (кабинет) больше не обновляет сессию, если токен доступа уже в памяти: в токене только
пользователь и сессия, а устаревший сам обновляется по 401. Раньше «reload» после сохранения «Ustawienia» и после
создания салона менял refresh-cookie, и перезагрузка страницы в эту секунду отправляла старый cookie → сервер
считал его повторным использованием (кражей) и закрывал сессию. Это и были «нестабильные» e2e `countries.spec.ts`
(Стамбул) и `booking.spec.ts` («90,00 €»); в них добавлено ожидание `networkidle` перед переходом.
Запрос обновления сессии идёт с `keepalive`, чтобы ответ (новый cookie) не терялся при переходе на другую страницу.
Если выходы всё же будут — можно дать серверу несколько секунд «льготы» на старый cookie (сейчас сознательно
строго: повтор = кража, это проверяют тесты `auth.spec.ts`).

## «Oceny klientów» в отчёте (задача 213)

`GET …/reports` возвращает `ratings`: `reviews` (отзывы о визитах периода — по дню визита, так что отзыв, написанный
позже, попадает в месяц визита), `average` (одна десятая, `null` без отзывов), `stars` (сколько отзывов на 1…5 звёзд)
и `staff` (мастера с отзывами: `average`, `reviews`, лучшие первыми). Права — как у отчёта: владелец и менеджер видят
весь салон, мастер с `viewOwnEarnings` — только свои визиты. Кабинет «Raporty» и бизнес-приложение показывают блок
«Oceny klientów: ★ 4,7» с полосками по звёздам и списком мастеров. Тест `apps/api/test/reports.spec.ts`, e2e
`reports.spec.ts` (скриншоты 74e, 75d).

## Бизнес-приложение: «Tydzień» (задача 214)

Кнопка «Tydzień» рядом с «Dziś» на экране дня открывает неделю (понедельник — воскресенье) одним запросом
